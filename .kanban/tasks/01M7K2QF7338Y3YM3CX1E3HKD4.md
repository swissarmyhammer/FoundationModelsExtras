## Why

A host (TestudoApp, "use the default skill marketplace") clears its stored marketplace list to go back to its default. Today it clears the settings value directly, so `MarketplaceRegistry` sends no change event, and the subscribers do not see the change. Only the host storage knows the default list, which is the list that applies after the stored value is cleared.

## What

In `Sources/Marketplace`:

- `MarketplaceSourceStorage` gets `func resetSources() async throws -> [MarketplaceSource]`. It clears the value of the host and gives the list that applies after that. A protocol extension gives a default: it saves an empty list and gives `[]`. Thus each storage that exists now still compiles.
- `InMemoryMarketplaceSourceStorage` gets an optional `defaultSources: [MarketplaceSource] = []` in its init. Its `resetSources()` sets the stored list to the default and gives it.
- `MarketplaceRegistry` gets `func reset() async throws -> [MarketplaceEntry]`. It runs in the same queue as the other writes, one at a time in call order. It reads the old list, calls `resetSources()`, and gives the new entries in list order. After the reset, it sends:
  - `.removed(oldEntry)` for each old id that is not in the new list,
  - `.added(newEntry)` for each new id that is not in the old list,
  - `.updated(previousID: id, newEntry)` for an id in both lists with a different source.
  - When the old and the new lists are the same, it sends no event.
- The order of the events: first the removals in old list order, then the additions and updates in new list order. Document it.
- A storage error comes out unchanged and sends no event. When the list that `resetSources()` gives is not valid (a duplicate id or a bad source), `reset()` throws the same error that `marketplaces()` throws for such a list, and sends no event. Document that the host has already cleared its value in this case.
