## Why
Router task ^est00wa found this defect. In `Sources/FoundationModelsExtras/ModelPool/ModelPool.swift` (about line 149), the release of the last `ModelHold` submits the eviction job from `Task.detached { try? await self.admissions.submit { await self.evictIfIdle(key) } }`. Thus an admission job that a caller submits after the last release can run before the eviction job. That job then sees the freed weights as still resident. The old router pool drained its pending releases before each measurement. With a tight budget, a resolve that the old pool accepted can fail.

## Requirement
The eviction job enters the admission queue synchronously inside `release`, in the same step as the hold count change. Every admission job submitted after the release runs after the eviction. The eviction job still checks the hold count again, so a new acquire before it keeps the model.

## Design
- Add to `GenerationQueue` one small synchronous, fire-and-forget enqueue (not async, no wait) that uses the same one-step count-and-yield as `submit` (see task ^38ybj4j). Share the code with `submit`. Do not duplicate it.
- In `ModelPool`, call it inside the same `Mutex` step that sets the hold count to zero. Remove the `Task.detached`.
- Keep the code simple. Add no lock, semaphore or gate types.

## Tests (write them first; show that the first test fails on the old code)
- [x] Release the last hold, then submit an admission job at once. The job sees no resident model, and `evict` ran one time. Repeat it many times in the test, so that the race shows on the old code.
- [x] A new acquire between the release and the eviction job keeps the model. This test exists already. It must still pass.
- [x] A unit test for the new synchronous enqueue: the order of the jobs is the enqueue order, also when it is mixed with `submit`.
