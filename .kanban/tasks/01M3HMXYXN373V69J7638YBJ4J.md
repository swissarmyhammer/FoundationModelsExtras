title: 'GenerationQueue: count a job and put it in the stream in one step, so the count order is the run order'

## Why
Integration test task 01M3HD789J538KVQHPY8XDYG55 found a real race with a real model: embed calls ran in the order 0, 1, 2, 4, 5, 3, although call 4 entered only after `waitingCount` showed call 3 as waiting.
The cause: in `GenerationQueue.submit`, `job.wait(continuation)` adds the job to the count (`unfinished`), and a separate call, `jobs.yield(job)`, puts the job in the FIFO stream. The two steps are not one atomic step, so a later submitter can yield first. The unit tests `GenerationQueueWorkerTests` and `PooledEmbedderTests` and the integration tests use the same "counted means queued" rule, so they have the same latent race.

## Decision
The count and the yield must be one step: when `waitingCount` shows a job, every job submitted after it runs after it. This makes the rule that the tests use a real guarantee.

## What to do (Sources/FoundationModelsExtras/ModelPool/GenerationQueue.swift)
- Replace the `Atomic<Int>` count with a `Mutex<Int>` on the queue. In `submit`, in ONE `withLock` of that mutex: move the job from new to waiting (`job.wait`), add 1 to the count, and `jobs.yield(job)`. If the job was already cancelled, do not count it or yield it.
- Lock order is always queue mutex, then job mutex. No code takes the queue mutex while it holds a job mutex: `Job.wait` does not change the count any more; `cancel` and `finish` subtract from the count only after they release the job mutex.
- `onQueued` uses the count value from inside that step.
- Keep the code small; no new types; short doc comment that tells the guarantee.

## Acceptance criteria
- [ ] A unit test that fails on the old code: many tasks submit concurrently; each submits only after `waitingCount` shows the job before it; the run order equals the count order.
